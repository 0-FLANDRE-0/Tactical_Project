## 2. 사용자 확정 설정

| 항목 | 확정 내용 |
|---|---|
| 아군·적군 차량 | 모두 **M1A2 (1998)**의 같은 게임 성능 |
| 해당 차량 최대 HP | **1,450** |
| 시험탄 | 양측 **M829A2 한 종류** |
| M829A2 100% 기준 차량 피해 | **405** |
| 피해 배율 | 아카이브에 기록한 A1형 게임 곡선을 공유 |
| 명중·부위 판정 | 기존 WIP10 판정 사용 |
| 입력 | 이번 단계는 수동 단발 발사를 유지 |

405는 배율 100%일 때의 기준값이다. 아카이브의 배율을 적용한 결과는 이 기준값에서 달라질 수 있다. A1의 기본 피해 380과 혼동하지 않는다.

이번 시험은 1998년형 구성을 사용한다. 1989년 본편 32종과 96개 프리셋에 M829A2를 일괄 추가하지 않는다. `M1A2 (1998)`를 SEP라는 이름으로 바꾸지 않는다.

## 3. 이번 실행 범위와 후속 범위

이번 단계는 다음 다섯 가지를 끝낸다.

1. 활성 시험 차량·탄약의 명시적인 데이터 연결.
2. 기존 내부 착탄 결과에 연결하는 게임 피해 처리.
3. 차량별 HP 누적과 단일 격파 전이.
4. 격파 차량의 행동 중단·잔해 표시·기존 접촉과의 정리.
5. UI, 재현 가능한 검증, HTML/ZIP, 문서.

다음 항목은 데이터·승인 범위가 더 필요하므로 후속으로 둔다.

- 전술적 판단과 자동 발사, 탄종 자동 선택.
- 생존 차량의 모듈별 손상·승무원 피해·수리·화재·유폭.
- ERA/BDD/D-Tech의 손상·소모와 다른 차종 추가.
- 고폭탄·파편·보병, 상세 장전·보급·탄약 프리셋 편집.
- 상부 피격 활성화, 세부 장갑 구획, 도탄·신관·새 물리 모형.

즉, 이번 단계의 기능 상실은 **격파 시 이동·관측·사격 기능이 종료되는 것**까지다. 살아 있는 차량의 ‘궤도만 파괴’ 같은 개별 기능 상실은 모듈 피해 단계에서 별도로 구현한다.

## 5. 프로파일과 데이터 연결

- 차량 형식과 탄약 ID를 명시한다. 권장 차량 ID는 `M1A2_1998`, 탄약 ID는 `M829A2`다.
- 아군과 적 관측 표적 모두 같은 활성 프로파일·탄약을 사용해야 한다. 표시명만 바꾸는 것으로 완료 처리하지 않는다.
- 새로 확정된 장갑·HP·탄약 게임 필드를 데이터로 분리하고 조회 경로를 하나로 유지한다. UI나 피해 함수에 별도 숫자 사본을 흩어 넣지 않는다.
- 기존 치수·기동·센서·도안 중 새로 정하지 않은 항목은 기존 시험 설정을 명시적으로 이어 쓴다. 이것을 1998년형의 새 실측 제원이라고 기록하지 않는다.
- 공유 프로파일은 불변 데이터, 현재 HP·탄수·격파 상태는 유닛별 런타임 데이터로 분리한다.
- 기존 `M1A2` ID를 호환성 때문에 남기면 그 용도를 문서화한다. 동결 fixture와 실제 시험 시나리오의 프로파일을 혼동하지 않는다.
- 프로파일·탄약 내보내기와 `data/vehicles/registry.json`을 갱신한다. 새로운 필드를 내보낸 파일과 실행 HTML에서 확인한다.
- 기존 도안·반경·지도·길찾기 계약을 유지한다. 이번 데이터 적용을 이유로 전장이나 내비게이션을 재제작하지 않는다.

## 6. 피해 처리의 책임과 연결 위치

### 6-1. 독립된 게임 상태 모듈

DOM·Canvas 없이 실행 가능한 피해/상태 모듈을 둔다. 예를 들어 `src/combat-state.js`처럼 분리할 수 있다. 파일명은 저장소 구조에 맞춰 조정하되 책임은 분리한다.

- 입력: 내부 착탄 ID, 실제 게임 명중 결과, 선택된 구역·좌우, 차량/탄약 게임 프로파일, 대상 런타임.
- 출력: 적용 여부·사유, 게임 방호 처리 결과, 계산된 HP 피해, 적용 전후 HP, 격파 전이 여부.
- 순수 계산과 상태 변경을 구분한다. 진단/UI 조회로 HP나 난수 상태가 변하면 안 된다.
- 사용자 곡선의 기준점과 범위 밖 처리를 테스트 가능한 게임 데이터로 관리한다.
- 기존 hit/zone/표시용 난수 스트림에 피해 계산을 섞지 않는다. 이번 HP 처리에 임의의 새 피해 추첨을 추가하지 않는다.

### 6-2. 내부 착탄 결과에서 정확히 한 번 처리

현재 `fire-control.js`의 `finishDue()`는 실제 결과를 계산한 뒤 공개 이벤트에서 미관측 정보를 숨긴다. **실제 피해는 공개용 `result:'unobserved'` 이벤트가 아니라 정제 전 내부 결과에서 적용한다.**

- 선택적 내부 콜백 등으로 시뮬레이션 코어에 결과를 전달한다. debug 기록을 다시 읽거나 UI에서 HP를 깎지 않는다.
- 발사 시점에 HP를 줄이지 않는다. 착탄이 해결되는 고정 스텝에서 처리한다.
- 빗나감은 대상 차량 HP를 줄이지 않는다.
- 한 발의 고유 ID당 적용은 한 번이다. 같은 이벤트 재조회·UI 갱신·중복 전달이 피해를 반복시키면 안 된다.
- 이미 격파되거나 제거된 대상에 대한 후속 처리는 명시적인 무효 사유를 남긴다.
- 관측이 끊겨도 내부 결과와 피해 처리는 진행된다. 숨겨야 하는 정보를 공개하는 일과 내부 피해 처리를 구분한다.
- 발사 뒤 사수 이동·선회·명령 취소·격파가 이미 발사된 탄을 삭제하거나 소급 변경하지 않아야 한다.
- 같은 시각 착탄의 기존 고정 처리 순서를 유지한다. 동시 사건의 순서와 결과를 문서화한다.

### 6-3. 기존 구역 계약 유지

- 차체/포탑 및 전·측·후의 구역 결과를 그대로 받는다.
- 차체와 포탑의 독립 방향, 측면 좌우 구분, 가려진 부위의 배제 규칙을 유지한다.
- `upper`의 현재 비활성 상태를 유지한다. 표시용 탄착 좌표에서 새 피격 부위를 다시 추첨하지 않는다.
- 방호·피해를 추가하면서 기존 명중 여부나 부위 결과를 다시 결정하지 않는다.

## 7. HP와 격파 상태

- 생성 시 각 차량에 독립된 최대 HP·현재 HP·생존/격파 상태를 초기화한다.
- 피해 뒤 HP는 유효 범위 안에 유지한다. NaN·음수 피해·알 수 없는 프로파일이나 구역을 방치하지 않는다.
- 격파 전이는 한 번만 발생한다. 격파 집계·효과·로그도 중복 생성하지 않는다.
- 격파된 차량은 새 이동·경계·지정·사격 명령을 수행하지 않는다. 대기 발사 요청과 자체 조준·관측 작업을 종료한다.
- 기존 고정 스텝에서 먼저 발사된 탄은 기존 비행 규칙에 따라 해결한다.
- 생존 차량의 기본 이동·후진·정지·관측·수동 사격 동작은 유지한다.
- 격파 차량의 위치에 잔해를 남긴다. 기존 동적 차량 점유 반경을 이용하고 정적 지도·베이크된 캐시를 변경하지 않는다.
- 잔해를 살아 있는 관측자나 새 사격 대상으로 계산하지 않는다. 잔해의 공개 여부는 기존 관측 정보 규칙에 맞춘다.
- 같은 ID로 시험장을 초기화해도 이전 HP·피해 적용 ID·격파·비행·접촉 상태가 넘어오지 않는다. 기록 저장량도 제한한다.

## 8. UI와 공개 정보

- 선택 아군 차량에 형식명, M829A2 탄약 표시, 현재/최대 HP, 생존 또는 격파 상태를 표시한다.
- 표적 상세에는 기존 공개 조건에서 허용하는 최근 게임 명중·방호·피해 결과를 표시한다.
- 아군의 자체 HP는 확인 가능하되, 적의 숨은 현재 HP·격파 여부·실제 좌표를 새 공개 경로로 노출하지 않는다.
- 기억 접촉에는 마지막으로 확인한 상태를 유지한다. 감춰진 세계 상태가 기억 표시를 실시간 갱신하면 안 된다.
- 미관측 결과는 기존처럼 미확인으로 취급한다. 사격 결과의 전면 공개 여부를 이번 작업에서 임의로 바꾸지 않는다.
- 격파 차량 선택·명령 버튼·발사 사유가 서로 일치해야 한다. 실행 불가능한 버튼은 상태와 사유를 보여준다.
- 재생/일시정지·초기화·차량 선택·화면 확대와 모바일 배치가 유지돼야 한다.
- 플레이 화면에는 내부 난수·실제 비공개 ID·개발용 수식을 기본 표시하지 않는다. 개발 진단은 별도로 둔다.

## 9. 빌드와 Worker 연결

- 새 모듈을 페이지의 스크립트 순서와 `build.py`에 포함한다.
- `visibility-client.js`에 넘기는 Worker용 소스 묶음도 확인한다. 새 전역 의존성 때문에 실제 Worker가 실패하고 대체 실행만 되는 상태를 통과로 기록하지 않는다.
- Worker가 필요 없는 피해 계산을 시야 Worker 안에서 별도로 중복 실행하지 않는다.
- 데이터 내보내기, 실행 HTML, 버전명, 개발 snapshot 버전을 WIP11A로 맞춘다.
- 외부 실행 의존성 없는 단일 HTML을 유지한다.

## 10. 필수 자동 검증

실장비의 효율이나 취약점 비교 대신, **합성 게임 fixture와 상태 전이**를 중심으로 검사한다.

| 번호 | 필수 확인 |
|---|---|
| V01 | 아군과 적의 활성 형식·탄약이 동일하고 최대 HP 1,450·기준 피해 405가 실제 조회 경로에서 사용됨 |
| V02 | 잘못된 ID·누락/비정상 게임 필드는 명확히 거부하고 상태를 부분 변경하지 않음 |
| V03 | 합성 입력에서 사용자 게임 곡선의 기준점·사이 구간·경계 처리가 일관됨 |
| V04 | 유닛별 HP가 분리되고 공유 프로파일을 변경하지 않음 |
| V05 | 발사 때 피해 없음, 착탄 해결 때 한 번 적용 |
| V06 | 같은 탄 ID 재전달·기록/UI 반복 조회로 추가 피해·추가 난수가 발생하지 않음 |
| V07 | 빗나감·이번 단계의 비관통·이미 무효인 대상 처리에서 HP 오류가 없음 |
| V08 | 미관측 명중도 내부 피해는 적용되고 공개 결과에는 숨은 상태가 새지 않음 |
| V09 | HP 0의 격파 전이·집계·표시가 한 번이며 새 행동을 거부함 |
| V10 | 사수 격파 전에 발사된 탄은 남아 있고, 제거/격파 대상에 대한 후속 사건이 안전함 |
| V11 | 같은 시각 여러 탄·여러 사수·대상 삭제가 고정 순서로 재현됨 |
| V12 | 동일 seed·명령·시뮬레이션 시간에서 배속/프레임 묶음·UI 조회 횟수와 무관하게 같은 HP·격파 결과 |
| V13 | 초기화와 같은 ID의 새 객체 생성 뒤 이전 피해·격파·비행 상태가 남지 않음 |
| V14 | 격파 후 접촉·표적 인계·명령·잔해 점유가 서로 모순되지 않음 |
| V15 | 기존 관측·LOS·차체/포탑 구역·확보/조준·발사 입력 회귀가 유지됨 |
| V16 | 내보낸 데이터·빌드 HTML·패키지의 활성 설정이 같고 오프라인 의존성이 완결됨 |

순수 계산 검사와 실제 `TacticalCore`를 통과하는 통합 검사를 모두 둔다. 새 설정을 그대로 읽어 비교하는 검사만으로 끝내지 않는다. 기존 동결 fixture를 현재 구현과 같게 고쳐 통과시키지 않는다.

기존 검사 예시:

```sh
node --test tests/ui-cache.test.cjs tests/look-animation.test.cjs tests/observation.test.cjs tests/observation-core.test.cjs tests/observation-correction.test.cjs tests/observation-moving.test.cjs tests/los-optimization.test.cjs tests/profile-registry.test.cjs tests/fire-control.test.cjs tests/fire-core.test.cjs tests/art-muzzle.test.cjs tests/hit-model.test.cjs tests/observation-metadata.test.cjs tests/game-flight.test.cjs tests/wip10-reference.test.cjs
node tests/input.test.cjs
node tests/map.test.cjs
node tests/visibility.test.cjs
node tests/vehicle.test.cjs
```

새 피해·격파 검사도 별도로 실행한다. WIP10 기준표의 역사적 검사와 WIP11A의 새 프로파일 검사를 구분한다. 새 프로파일 때문에 합리적으로 바뀐 기본값·UI 버전 기대값은 이유를 명시해 갱신한다.

## 11. 브라우저·성능 확인

실제 브라우저에서 단일 HTML을 실행해 아래 흐름을 확인한다.

1. 새 시험장 생성, 양측 형식·탄약과 아군 HP 표시.
2. 실제 관측·인계/확보·조준 후 수동 발사, 비행 중 HP 유지, 착탄 후 HP 갱신.
3. 누적 피해와 격파, 이후 명령 거부, 잔해 표시.
4. 일시정지·초기화·차량 선택·미식별/기억/미관측 결과.
5. 데스크톱과 모바일 가로·세로 viewport의 버튼·패널·수평 넘침.
6. 실제 내장 시야 Worker와 오류 시 대체 경로의 구분.

브라우저 실행은 직접 시도한다. 환경 제한으로 실패하면 정확한 오류와 실행하지 못한 항목을 기록한다. 로컬 HTTP 검증을 더블클릭 `file://` 검증으로 바꾸어 적거나, viewport 검사를 실제 Android 실기기 검사로 적지 않는다.

기존 관측 벤치마크를 실행해 동일한 조건의 CPU 결과를 남긴다. 추가로 여러 착탄을 한 시점에 처리하는 합성 게임 부하를 확인하고 중복 피해·무제한 기록·심한 지연이 없는지 본다. CPU 처리 시간을 전체 게임 FPS로 환산하지 않는다. 오래 걸리는 전장 재수집·재베이크는 이번 작업에 포함하지 않는다.

## 12. 산출물과 문서

- 소스에서 다시 빌드하고 `python3 scripts/package_release.py WIP11A`로 패키징한다.
- `Tactical_v0.4_WIP11A.html`과 `dist/index.html`의 바이트 일치를 확인한다.
- ZIP은 실행 HTML 한 파일을 포함한다. CRC, 압축 해제 바이트, SHA-256을 확인한다.
- `SHA256SUMS_WIP11A.txt`와 릴리스·검증 기록을 만든다. 이전 HTML/ZIP/검증 자료는 보존한다.
- 구현 문서에는 데이터 필드, 내부 착탄 연결, 임시 게임 정책, 공개 정보, 격파 처리 순서와 미구현 범위를 적는다.
- `README.md`, `archive/NEXT_STEPS_2026-11-07.md`, 해당 데이터의 코드 적용 상태를 갱신한다. 보병 백업과 기존 탄약·장갑 수치를 덮어쓰지 않는다.
- 완료한 코드·HTML·ZIP·문서·검증 결과를 같은 작업 브랜치에 모은다. 기존 작업 브랜치/PR이 있으면 이어서 갱신하고 대체 작업을 중복 생성하지 않는다. 강제 푸시·사용자 변경 삭제는 하지 않는다.
