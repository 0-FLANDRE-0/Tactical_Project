# WIP07B LOS 최적화

2026-11-07. WIP07A `e9f037cc6edca994e3f19297d3e0aa6c491be164`에서 이어서 구현했다. 시작 시 작업 트리는 깨끗했고 AGENTS.md는 없었다. PR #3은 미병합 초안이었다. main `776f02c`의 추가 변경은 설계 아카이브뿐이어서 기존 `feat/wip07-observation` 브랜치에 동기화해 보존했다. 게임 기능으로 끌어오거나 아카이브 값을 수정하지 않았다.

사용자가 남긴 임시 실험 설명의 32m 구역 요약을 실제 코드에 구현했다. 이전 실험 파일은 전제하지 않고 현재 원본과 독립적으로 대조했다. 현재 관측 규칙은 [WIP07A 상태 문서](OBSERVATION_WIP07A.md)를 유지한다. 변경한 실행 로직은 `src/sim-core.js`의 정적 파생 요약과 `lineOfSight` 순회다. `observation.js`, 센서 프로파일, 20Hz/10Hz 주기, 9개 관측점, 탐지/식별 확률·감쇠·기억·명령·기동은 바꾸지 않았다.

## 무엇을 건너뛰는가

4000×4000m 지도를 32×32m 타일 125×125개로 나눈다. 코어 인스턴스마다 한 번 다음을 요약한다.

| 요약 | 구성 | 보수적인 경계 |
|---|---|---|
| 지형 최대 높이 | Float64, 15,625개 | 해당 타일에서 보간에 참여할 수 있는 모든 2m 높이 표본. 가장자리 이웃 정점도 포함 |
| 건물 최대 높이 | Float64, 15,625개 | 타일과 바운딩 박스가 겹치는 모든 건물 지붕과 표시용 roof atlas의 높이. preview atlas의 기본 높이 0도 포함 |
| 숲/관목 유무 | Uint8, 15,625개 | 해당 타일의 4m 지표 분류가 forest/scrub인지 확인 |

배열 크기는 총 **265,625바이트**다. 원본 높이장·지도·건물·숲 데이터를 변경하거나 다시 양자화하지 않는다. 같은 정적 지도의 파생 가속 자료일 뿐이다. 본문과 내장 Worker는 각 코어를 만들 때 독립적으로 한 번 구성한다. 차량마다 이 요약이나 전체 시야 마스크를 다시 만들지 않는다.

광선은 원래와 똑같은 `n=ceil(거리/2m)`의 내부 표본 격자를 사용한다. `fast=true`의 기존 6m preview 격자도 유지한다. 현재 표본이 속한 타일을 떠나기 전까지의 표본 인덱스 범위를 계산하고, 마지막 원본 표본이 실제로 같은 타일인지 확인한다. 역방향·정확한 경계·부동소수점 반올림으로 범위가 애매하면 범위를 줄인다. 새 격자를 만들거나 표본 시작점을 타일 경계로 옮기지 않는다.

범위 전체의 가장 낮은 광선 높이가 지형 최대 높이보다 충분히 높고(기존 0.06m 허용 기준 유지), 건물 최대 높이보다 높으며, 숲이 없거나 숲 수관 최대 높이보다 높을 때만 통과를 확정한다. 0.0000001m의 추가 보수적 여유는 경계에서 정밀 검사 쪽으로 보내기 위한 값이다. 통과를 쉽게 만드는 오차 허용값이 아니다.

하나라도 확실하지 않으면 해당 구간의 **모든 원래 2m 표본을 원래 순서대로** 검사한다. 건물은 기존 정확한 다각형 판정을 사용한다. 지형·건물·숲 중 어떤 것이 먼저 가리는지와, 그때까지의 숲 광학 깊이도 그대로 반환한다. 지도 밖/비유한 입력은 전체 원본 세밀 순회로 처리한다.

## 결과가 유지되는 이유

- 보간된 높이는 이웃 정점 범위 안에 있으므로, 이웃까지 포함한 최대 높이는 타일 내부 지형의 상한이다. Float64 요약으로 최대값을 아래로 반올림하지 않는다.
- 건물 지붕의 바운딩 박스를 넓게 포함하므로 얇은 건물·안뜰·구멍·윤곽 경계는 통과를 함부로 확정하지 않고 기존 다각형 검사로 넘어간다.
- 숲이 있거나 수관 높이 조건이 애매한 구간에서는 원래 광학 깊이 덧셈을 전부 수행한다. 광학 깊이를 묶어서 근사 적립하거나 누적 순서를 바꾸지 않는다.
- 통과를 확정한 구간은 원래 검사에서도 광학 깊이에 0만 더할 구간이다. 따라서 이후 차폐 사유와 `forestDepth`까지 정확히 보존한다.
- 이동/자세/높이에 따른 기존 광선 캐시 무효화는 그대로다. 이 요약은 움직이는 유닛의 옛 visible 결과를 재사용하는 캐시가 아니다.

정적 지도 전제는 기존 코어와 같다. 향후 건물 파괴·동적 지형을 추가하면 원본 충돌/지붕 자료와 함께 이 파생 요약도 갱신해야 한다. 이번에 그런 판정을 추가하지 않았다.

## 독립 원본 대조

`tests/fixtures/sim-core-WIP07A.js`는 원본 커밋의 전체 코어를 바이트 그대로 보존한 검사 전용 파일이다. 원본 SHA-256은 `ab70525f12138b068daf00198bd49611d883c940cd8ac8c6fcfeac5a55f2e49c`다. 검사 로더가 해시를 확인한다. 런타임 HTML·Worker에는 들어가지 않는다. 원본 브랜치로 체크아웃하거나 네트워크로 다시 읽지 않고 비교할 수 있다.

`tests/los-optimization.test.cjs`는 단순 visible 여부만 비교하지 않는다. `visible`, `reason`, `forestDepth`, 전체 노출 결과와 9개 표본을 정확히 대조한다. 실제 지도 12,000건(정밀 8,000/preview 4,000)에 추가 경계 사례를 더한 **LOS 13,805건**, **노출 1,000건**이 원본과 일치했다. 노출 검사는 별도로 총 9,000개 부위 광선을 사용한다.

경계 사례에는 32m/지도 경계, 양/음 진행 방향, 수평/수직/대각/영길이, 범위 밖, 얇은 건물, 다각형 안뜰, 능선, 0.06m 접선, 15m 수관 경계, 숲/관목의 양방향 누적을 포함한다. preview roof atlas의 빈 셀 높이 0도 보수적으로 처리한다.

기존 관측·움직임·차폐·기억·팀 공유·입력·Worker 회귀와 실제 브라우저 검사를 함께 실행했다. 결과는 [릴리스 노트](../TACTICAL_RELEASE_WIP07B.md)와 `tests/releases/WIP07B-validation.json`에 남긴다. A 버전의 결과 파일을 새 결과로 덮어쓰지 않는다.

## 성능 비교 재현

```sh
python3 build.py
node --test tests/los-optimization.test.cjs
node scripts/benchmark_observation.cjs
node scripts/benchmark_los_compare.cjs
```

공통 fixture는 `scripts/observation-benchmark-fixture.cjs`다. WIP07A의 실제 지도·seed 407·정지/이동 50·100대·20스텝 준비/100스텝 측정·결정적 궤적을 그대로 사용한다. 궤적 생성은 스텝 CPU 시간에서 제외한다.

비교 스크립트는 기준/최적화 코어를 **별도 새 프로세스**에서 순차 실행한다. 3회씩 실행하고 실행 순서를 교대한다. 각 프로세스는 같은 네 가지 시나리오를 실행한다. 최종 시나리오·차량별 접촉·팀 접촉·관측/캐시 횟수를 포함한 JSON을 바이트 단위로 대조하며 모두 같다. 각 경우의 SHA-256과 개별 실행 수치도 남긴다.

요약 중앙값과 P95는 각각 프로세스별 통계값 세 개의 중앙값이다. 최대값은 모든 실행에서 관측한 실제 최대 스텝이다. 원시 데이터는 `tests/releases/WIP07B-comparison.json`에 있다. 로더의 초기화 시간은 읽기/평가 경로가 다르므로 요약 생성 시간의 전후 비교로 사용하지 않는다. 성능값은 관측을 포함한 시뮬레이션 스텝 CPU 시간이며 전체 게임 FPS가 아니다.

## 빌드와 다음 진입점

정식 결과는 WIP07B HTML과 ZIP으로 만든다. `build.py`·본문 script 순서·Worker 소스 목록은 그대로다. 새 런타임 모듈이 없으며 비교용 원본·검사·벤치마크는 번들에 포함하지 않는다. `python3 scripts/package_release.py WIP07B`가 HTML/dist 일치, ZIP CRC와 압축 해제 결과를 확인한다. 완료 응답은 GitHub ZIP 직접 다운로드를 제공한다.

추가 성능 작업은 이 보수적 통과 조건을 유지한 정밀 구간 내부의 중복 조회/자료 접근 검토가 진입점이다. 숲이 많거나 지형 상한에 가까운 광선은 의도적으로 정밀 검사로 돌아가므로 모든 배치에서 같은 개선율을 보장하지 않는다. 실제 Android 지속 FPS·발열·배터리·터치는 별도 실기기 검증 대상이다.
