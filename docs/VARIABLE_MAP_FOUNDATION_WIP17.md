# WIP17 가변 맵 크기 지원 기반

## 완료 범위

WIP17은 현재 4×4km 라스도르프를 바꾸지 않고, 같은 2m/4m/16m 해상도로 다른 폭과 높이의 지도를 넣을 수 있는 규격·빌드·검증 기반을 추가한다. `src/map-spec.js`가 지도 ID/해시, 월드 폭·높이, 고도·지표·길찾기 격자를 대용량 디코드 전에 검증한다. 지원 계약은 정수 미터, 폭·높이 각각 최대 8000m, 16m 정렬이며 2m 고도 표본 원점 1m, 4m 지표, 16m 길찾기를 고정한다. 부분 nav 셀은 조용히 만들지 않고 거부한다.

이번 배포에는 실제 8×8km DEM/OSM 지도가 없다. 합성 대형 자료는 검사 중 임시 디렉터리에 생성하고 기본 HTML/ZIP에 넣지 않는다.

## 런타임과 캐시

- `sim-core.js`는 규격 검증 뒤에만 고도·지표·nav·지붕·LOS 요약 배열을 만든다. 4km 고정 허용문을 제거하고 nav 행/열을 공통 규격에서 가져온다.
- 지표 지붕 격자의 `999`, `1000`, `4` 고정 인덱스를 실제 지표 행/열/간격으로 교체했다. 건물 공간 버킷의 y 경계가 열 수를 쓰던 오류도 별도 행 수로 고쳤다.
- 페이지, Worker, Node 로더가 모두 `map-spec`을 지도 뒤·코어 앞에 로드한다. Worker는 본문과 같은 내장 지도/규격 모듈을 사용한다.
- 등고선과 지형 판독성 자료에 `mapSpec` 서명을 추가했다. 필수 등고선이나 제공된 선택 자료의 지도 해시·폭/높이·각 격자가 다르면 즉시 실패한다. 선택 자료 자체가 없으면 기존 기본 지형 표시로 폴백한다.
- 카메라·클릭·지도 테두리는 기존 `WORLD.w/h` 흐름을 유지했고, 제목·헤더·정보·footer의 크기는 빌드에 선택한 지도 메타데이터로 만든다.

기존 라스도르프 `mapHash`와 높이·지표·feature·nav 데이터는 그대로다. 등고선의 89개 선과 정점 배열도 동일하며 규격 서명만 추가됐다. 지형 판독성 선 106개도 동일하고 서명만 추가됐다.

## 생성과 빌드

기본 명령은 이전 4×4 입력/출력을 유지한다.

```sh
/usr/bin/python3 scripts/build_battlefield.py
node scripts/bake_navigation.cjs
/usr/bin/python3 scripts/build_contours.py
/usr/bin/python3 scripts/build_terrain_readability.py
python3 build.py
```

새 실측 지도를 준비한 뒤에는 `data/map-build-rasdorf-4km.json`과 같은 설정에 원본 경계·DEM·OSM·출력을 지정한다. 각 파생 도구는 `--input`, `--output`, `--script-output`을 받고, `build.py`는 `--map`, `--contours`, `--terrain`, `--output`으로 한 묶음을 선택한다. 서로 다른 지도의 파생물을 섞으면 출력 파일을 만들기 전에 거부한다.

```sh
python3 build.py --map /path/map.json --contours /path/contours.json \
  --terrain /path/terrain.json --output /path/index.html
```

현재 원본을 다른 범위로 늘여 만든 제품용 지도는 지원하지 않는다. 새 범위를 덮는 실제 DEM/OSM과 일치하는 nav/파생물이 필요하다.

## 합성 검증과 비용

`tests/helpers/variable-map-fixture.cjs`는 실제 크기의 배열을 만든다. 8×8은 고도 4000×4000(1,600만 셀), 지표 2000×2000(400만 셀), nav 500×500이며 사전 nav를 포함한다. 직사각형은 8×4.096km와 작은 비대칭 인덱스 fixture를 함께 쓴다. 평탄한 메타데이터 위장을 피하려고 비대칭 고도/지표 표본과 남쪽 건물 차폐를 검사한다. 4km 밖에 놓은 두 차량은 실제 관측·식별·수동 지정·조준을 거쳐 발사와 탄착을 완료하며, 포구·탄착 좌표와 연결된 비행/충돌 효과가 모두 4km 밖에서 생성되는지 확인한다.

AMD EPYC 9V74, Node v24.22.1, Chromium 156 환경의 순차 측정이다. 전체 FPS나 모바일 보장은 아니다.

| 조건 | 라스도르프 4×4 | 합성 8×8 |
|---|---:|---:|
| 코어 초기화 중앙값 / 3회 최대 | 85.23 / 125.35ms | 258.11 / 350.18ms |
| 20대 쌍 틱 중앙값 / P95 | 1.11 / 4.66ms | 1.46 / 2.71ms |
| 짧은 경로 중앙값 / P95 | 4.44 / 10.28ms | 3.10 / 8.78ms |
| 긴 경로 중앙값 / P95 | 22.34 / 24.11ms | 67.47 / 72.65ms |
| 긴 경로 방문 셀 | 30,785 | 108,273 |
| 주요 런타임 배열 산술 합계 | 21,578,125B | 86,312,500B |

8×8 실제 Chromium의 24개 강제 지도 재구성은 중앙값 7.7ms, P95 14.6ms였다. 같은 페이지의 `performance.memory.usedJSHeapSize`는 약 230.8MB였지만 Worker 프로세스와 브라우저 전체 메모리는 포함하지 않는다. 4km 밖 `(5200, 5200)`에서 내장 Worker 응답은 485ms였고 폴백은 발생하지 않았다. 원자료는 `tests/releases/WIP17-map-benchmark.json`과 `WIP17-browser.json`이다.

## 남은 작업

- 실제 8×8km 원본 수집·출처 검증·지도 편집과 제품 배포
- 대형 실측 지도에서의 장애물 밀도·긴 A* 성능 검토 및 필요 시 계층형 길찾기
- 복수 지도 선택, 실행 중 교체, 스트리밍/청크 로딩
- 실제 모바일 기기의 메모리·열·입력·프레임 측정

WIP16의 관측·표적 선택·차폐 재확인·halt 무발사 검사와 기존 전투 확률/난수 규칙은 변경하지 않았다.
