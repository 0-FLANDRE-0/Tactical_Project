## 4. 구현의 첫 접근 — 같은 경로의 조회 공유

`exposure()`는 같은 차체 평면 위치에서 높이가 다른 두 표본을 각각 검사한다. 두 광선은 목표 높이가 달라도 수평 경로와 기존 거리 표본 위치가 같다. 이때 반복되는 지형 조회를 공유하는 접근을 우선 실험한다.

1. **실제로 같은 수평 경로인 표본만 묶는다.** 관측 위치·눈높이와 표적 x/y, 거리 분할 수와 표본 격자가 정확히 일치하는지 확인한다. 가까운 경로를 근사하여 합치지 않는다. 포탑 표본이나 다른 프로파일도 같은 조건을 만족할 때만 공유한다.
2. 같은 표본 위치의 지면 높이·지표 조회·정적 구역 정보처럼 결과가 같은 값을 한 번 읽어 재사용한다. 건물 검사의 공통 후보/다각형 내부 여부를 공유한다면 높이별 지붕 차폐 판단은 독립적으로 수행한다.
3. 각 광선의 높이·숲 누적값·차폐 사유·완료 상태는 별도로 유지한다. 낮은 표본이 가려졌다고 높은 표본까지 종료하거나, 높은 표본이 보인다고 낮은 표본을 통과시키지 않는다. 한 광선이 종료된 뒤 남은 광선에 필요한 조회만 이어간다.
4. 표본별 32m 건너뛰기 가능 여부가 달라질 수 있다. 공통 순회 때문에 어느 광선의 원래 검사를 빠뜨리면 안 된다. 애매한 경우 기존 단일 광선 경로를 사용한다. 결과가 같아도 순회 범위가 늘어 더 느려지는 배치는 별도 측정한다.
5. 캐시 적중 여부도 표본별로 처리한다. 모두 적중, 일부만 적중, 전부 미적중인 경우를 나눈다. 적중한 결과를 새로 계산하거나 cache timestamp를 임의로 연장하지 않는다. 공유 가능한 표본이 하나뿐인 경우 기존 경로를 사용할 수 있다.
6. 반환 표본은 원래 순서로 만든다. 내부 scratch 공간을 재사용해도 이전에 반환한 노출/접촉 결과가 다음 호출로 변하지 않게 한다. 공개 객체와 캐시 내부 작업 버퍼를 같은 참조로 묶지 않는다.
7. 원래의 공개 `lineOfSight()`·`exposure()` 호출 계약과 등록 프로파일/override를 유지한다. 특수 입력·범위 밖·영길이·음수 진행 방향은 기존 의미로 처리하고, 최적화 대상이 아니면 검증된 원래 경로로 보낸다.
8. 기능 플래그나 두 개의 독립 판정 엔진을 제품 설정에 남기지 않는다. 기준 구현은 검사 전용으로 보관하고, 런타임에는 채택한 작은 경로와 필요한 폴백만 둔다.

처음부터 전체 높이장 캐시를 하나 더 만들거나, 모든 관측자/표적의 결과를 저장하는 무제한 전역 캐시를 추가하지 않는다. 조회 공유를 위한 준비·분기·할당 비용도 이득 계산에 포함한다.

## 5. 독립 기준과 정확한 동등성 검증

- 구현 전에 작업 기준을 고정한다. 시작 시 코드가 현재 main과 같다면 `src/sim-core.js`의 SHA-256은 `8ee5cc9f4374db0afcffaf9ae49df9e6c818a089fd72a7f1319f29c994788ee8`이다. 이후 원격 변경이 있으면 차이를 확인하고 새 기준 commit/hash를 명시한다.
- WIP11D 기준 코어를 별도 검사 fixture로 보존하고 해시를 검증한다. 최적화한 helper를 기준 구현에도 주입하거나, 기준값을 새 결과로 재생성하지 않는다. fixture와 비교 도구는 실행 HTML·Worker 번들에 포함하지 않는다.
- 기존 WIP07A 원본 oracle과 동결 명중/비행 기준표는 그대로 둔다. 이 원본은 기하 판정의 독립 검증에 유용하지만, WIP11D 전체 전투/관측 상태를 비교하는 유일한 기준으로 사용하지 않는다. 전체 시뮬레이션은 같은 WIP11D 규칙끼리 비교한다.
- 실제 지도에서 기존 LOS 12,000건·노출 1,000건 이상의 대조를 유지하고, 최적화 경로가 실제 호출되는 새로운 다중 높이·캐시 대조를 추가한다. `visible`만 비교하지 말고 `reason`, `forestDepth`, 9개 표본 전체·메타데이터·집계값을 정확히 비교한다.
- 합성 지형/구조물에는 평지, 능선 접선, 얇은 건물, 안뜰, 숲/관목·수관 경계, 32m/지도 경계, 정·역방향, 수평/수직/대각선, 영길이, 범위 밖을 포함한다. 한 높이만 가려지는 경우, 표본마다 먼저 만나는 차폐 종류가 다른 경우도 포함한다.
- 캐시는 새 호출·전체 적중·부분 적중·유효기간 직전/직후, 관측자/표적 이동·독립 차체/포탑 회전·눈높이 변경을 대조한다. 직전 호출의 반환 객체가 후속 호출로 변하지 않는지도 확인한다.
- 공유 경로가 적용되는 표본 묶음/조회 수를 검사에서 확인한다. 실제로는 모두 기존 경로로 폴백하면서 통과한 검사를 최적화 검증으로 보고하지 않는다.
- 같은 seed·명령·시간 간격에서 탐지/식별/상실 시각, 표본 노출, 공개 접촉·HP·기억·잔해, 인계/경계, 관련 게임 이벤트와 상태가 기준과 일치해야 한다. 보류/자동 모드 둘 다 확인한다.
- 성능 측정용 새 진단 필드는 비교에서 명시적으로 분리할 수 있지만, 기존 게임 상태·난수·이벤트·기존 통계의 차이를 넓게 제외해 통과시키지 않는다. 시간 측정값을 게임 상태에 넣지 않는다.

## 6. 성능 측정과 채택 기준

1. 기존 `scripts/observation-benchmark-fixture.cjs`의 seed 407, 0.05초 스텝, 준비 20·측정 100스텝, 정지/이동 50·100대, 동일 궤적과 양 팀 관측을 유지한다. 캐시가 잘 맞도록 움직임·대상 수·시야를 줄이지 않는다.
2. 기준/최적화는 **별도 새 프로세스에서 순차 실행**하고 실행 순서를 교대한다. 최소 3회씩 측정하며 다른 벤치마크를 동시에 돌리지 않는다. CPU 프로파일은 원인 분석용이고 프로파일 없는 본 측정과 섞지 않는다.
3. 사례별 중앙값·P95·최대, 초기화 비용, 반복 메모리/할당 추이, 캐시 적중/미적중을 남긴다. 최종 상태를 정확히 대조하고 비교 대상 head·소스 해시·Node/CPU·지도 해시·원시 실행값을 기록한다.
4. 원래 광선 수와 줄어든 내부 작업을 구분한다. `rayQueries`·`rayCacheHits` 등 기존 통계 의미를 유지하고, 필요하면 별도 진단으로 고도 조회 수·공유 묶음 수·구역/세밀 표본 조회 수를 기록한다. 9개 논리 광선을 한 함수로 처리했다는 이유만으로 광선 수가 줄었다고 보고하지 않는다. 계측을 끈 상태에서도 성능 이득을 확인한다.
5. 기존 네 사례 외에 숲·마을·접선 능선의 고정 배치와, 여러 광선이 일찍 막히는 배치를 대조한다. 배치·좌표·조건을 남기고 최적화에 유리한 개활지만 골라 결론내리지 않는다.
6. **목표는 이동 100대 스텝 중앙값 10% 이상 개선**이다. 이는 보장값이 아니다. 같은 조건의 반복 측정에서 이득을 확인하고 P95가 지속적으로 악화되지 않아야 한다. 다른 기본 사례에서 5%를 넘는 지속적 악화가 보이면 원인을 조사한다. 결과가 잡음 범위이거나 엇갈리면 5회로 늘려 확인하고 측정 조건을 바꾸지 않는다.
7. 목표에 못 미치면 개선율과 복잡도를 함께 평가한다. 전체 스텝은 그대로인데 microbenchmark만 빨라진 변경, 흔한 배치에서 더 느린 변경, 재현되지 않는 작은 이득은 성공으로 포장하지 않는다. 효과가 없는 구현은 되돌리고 기준·대조 검사·측정 결과·후속 제안만 검토 가능하게 남긴다. 이 경우 최적화 완료나 새 실행 버전 출시로 보고하지 않는다.

이번 목표는 판정 보존과 의미 있는 CPU 비용 감소다. 과거 서버 수치와 다른 기기 수치를 나누어 개선율을 만들거나, CPU 스텝 시간을 게임 FPS로 바꾸어 표현하지 않는다.

## 7. 전체 회귀·브라우저·패키지

- 채택 후보가 정해지면 실제 프로젝트의 전체 Node 회귀를 실행한다. 현재 실행 예는 `node --test --test-concurrency=2 tests/*.test.cjs`다. 자체 검사 수를 출력하는 입력·지도·시야·차량 파일의 내부 검사 수와 Node 러너의 파일 단위 집계를 중복 합산하지 않는다.
- 새 동등성/성능 도구에는 실패 시 비정상 종료를 유지한다. 결과 파일은 이번 run의 대상/버전과 일치해야 한다. 이전 릴리스 기록을 새 측정으로 덮어쓰지 않도록 출력 경로를 해당 WIP용으로 분리한다. 독립 기준표·원본 oracle은 변경하지 않는다.
- 기존 지형 재현성·원본 자료 검사를 실행해 지도·파생 데이터가 변하지 않았음을 확인한다. 원본 재수집·고도 재양자화·길찾기 재베이크는 하지 않는다.
- 실제 Chromium에서 단일 HTML, 내장 시야 Worker, 일반/지형 × 등고선 켜짐/꺼짐, 시야 홀드, 가로 UI·세로 차단/복귀, 공개 HP·경계/관측 관련 회귀를 확인한다. 새 모듈이 필요하면 본문과 Worker의 소스 순서/의존성도 함께 검증한다. 관측을 Worker로 이전하는 작업은 아니다.
- 실제 게임이 도는 브라우저에서도 작은 재현 배치와 50/100대 대표 배치의 시뮬레이션 스텝을 비교해 Node에서의 개선이 유지되는지 확인한다. 페이지 오류·긴 입력 정지·메모리 증가가 없는지 기록한다. headless viewport를 실제 모바일 기기 검증으로 표현하지 않는다.
- 코드가 채택되면 WIP11E 버전·빌드·`python3 scripts/package_release.py WIP11E`를 맞춘다. 소스 빌드 = dist = 버전 HTML, ZIP 단일 HTML·CRC·해제 바이트·SHA-256 및 반복 패키징 바이트 일치를 확인한다. 이전 실행 파일은 보존한다.
- 현재 `file://`는 환경 정책으로 차단될 수 있다. 실제 오류와 미실행 항목을 남기고 같은 단일 HTML을 로컬 HTTP에서 검증한다. 실행하지 않은 브라우저/실기기 검사를 통과로 적지 않는다.
