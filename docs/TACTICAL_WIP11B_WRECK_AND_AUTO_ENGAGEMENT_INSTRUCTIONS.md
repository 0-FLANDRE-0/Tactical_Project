생존 차량의 모듈·승무원·화재·유폭·수리, 다른 차종·탄종, 장전 상세·재보급, 보병·파편, 세부 장갑 구획은 이번 범위에 넣지 않는다.

## 3. 작업 A — 잔해 처리 수정

### 3-1. 재현된 두 문제부터 회귀 검사로 고정

검토한 WIP11A에서 다음을 실제 코어로 재현했다.

1. 미관측 상태에서 적이 격파되면, 다시 그 위치를 관측해도 잔해를 식별할 수 없다. 일반 기억이 만료된 뒤에는 접촉이 없어지지만 실제 점유는 남는다.
2. 공개 접촉·공개 착탄 결과가 동일한 두 경우에도, 숨겨진 실제 상태가 생존이면 기억 접촉 지정 성공, 격파면 실패한다. 명령 반응이 미확인 격파를 노출한다.

현재 원인은 `TacticalCore.step()`이 격파 차량을 관측 입력에서 통째로 제거하고, `deadContact()`/지정 경로가 비공개 실제 격파 상태로 공개 명령을 거부하는 데 있다. 코드를 고치기 전에 이 두 시나리오를 재현하는 검사를 남긴다.

### 3-2. 관측자와 관측 후보 분리

- 살아 있는 차량만 관측·경계·인계·사격의 수행자가 된다.
- 격파 차량도 잔해 발견·식별의 대상에는 남긴다. 살아 있는 관측자 목록과 관측할 대상 목록을 분리하는 등 현재 구조에 맞게 연결한다.
- 미확인 잔해는 일반 살아 있는 교전 표적으로 새 인계하지 않는다. 잔해 상태 인식은 실제 관측·식별을 거쳐 갱신한다.
- **생전의 식별 기록만으로 보이지 않는 격파를 확인 처리하지 않는다.** 이후 실제로 잔해 상태를 관측·식별하는 근거가 있어야 한다.
- 기존 LOS·채널·탐지/식별 누적 규칙을 재사용한다. 새 탐지 거리·시간·특수 능력 수치를 추가하지 않는다.

### 3-3. 팀별 영구 공개 사본

- 실제 잔해는 전투 종료/초기화까지 남고 기존 동적 점유 반경을 유지한다.
- 격파를 관측해 잔해로 확인한 경우와, 미관측 격파 뒤 나중에 식별한 경우를 같은 공개 경로에 연결한다.
- 한 번 확인한 팀에는 시야 상실·접촉 기억 만료 후에도 잔해를 계속 표시한다. 다른 팀에 자동으로 공개하지 않는다.
- 공개 사본에는 확인한 위치·자세·표시용 모델과 필요한 잔해 상태만 둔다. 비공개 실제 상태를 렌더링 조회 때 따라 갱신하지 않는다.
- 일반 접촉과 잔해가 중복 표시되거나 이미 확인한 잔해가 살아 있는 표적으로 되돌아가지 않게 한다.
- 같은 잔해에 여러 관측자가 접근해도 공개 사본은 중복 생성하지 않는다. 로그 수 제한을 이유로 확인된 잔해를 삭제하지 않는다.

### 3-4. 선택·명령·화면

- 아군·적군 잔해 모두 지도 클릭/터치, 명단, 선택 순환, 표적 지정과 AI 교전 후보에서 제외한다. 보이지만 눌리지 않는 전장 잔해로 취급한다.
- 단순히 지정 버튼을 비활성화하는 것으로 끝내지 않는다. `pickUnit`, `select`, 개발 입력 API 등 실제 선택 진입점을 확인한다.
- 현재 선택 차량이 격파되면 생존 아군으로 선택을 옮긴다. 생존 아군이 없으면 선택 없음 상태를 정상 지원한다.
- `selectedUnit()`, `lookView()`, 시야 Worker 요청, 사격/UI/snapshot과 단축키가 선택 없음 상태에서 예외를 내지 않아야 한다. 지도 이동·확대·일시정지·초기화는 계속 사용할 수 있어야 한다.
- 기존 잔해를 클릭하면 잔해 선택을 가로채지 않고 기존 지면 입력 규칙을 따른다. 잔해 점유는 유지한다.
- 숨겨진 격파 상태만으로 기억 접촉 지정의 수락 여부·공개 사유·버튼 상태를 바꾸지 않는다. 확인된 잔해만 공개 정보에 따라 지정 대상에서 제외한다.
- 명령 수락과 실제 발사 허용은 별개다. 기억 접촉을 지정해도 자체 관측·확보가 없으면 발사하지 않는다.
- 격파로 표적 선택이 해제돼도, 이미 공개가 허용된 최근 착탄 결과는 아군의 최근 결과 표시 등 적절한 위치에 남길 수 있다. 잔해를 선택하게 만들어 결과를 읽게 하지 않는다.

## 4. 작업 B — 기본 자동교전

### 4-1. 이번 기본 정책

아래는 이번 구현 범위를 구체화하는 기본 정책이다. 장기 OODA 전체 설계의 확정으로 취급하지 않는다.

| 항목 | 구현 정책 |
|---|---|
| 차량별 자동 사격 모드 | `auto` / `hold` 두 가지. 화면에는 **자동 사격 / 자동 사격 보류**로 표시 |
| 실행·생성 기본 | 양측 정상 차량 생성·초기화·신규 시나리오의 기본값은 `auto`. 플레이어는 표적 지정 후 별도 발사 입력 없이 교전 가능 |
| 기존 수동 시험/호환 fixture | 수동 단발 계약을 검사하는 fixture만 `hold`를 명시. 테스트 때문에 정상 차량 생성 기본을 hold로 두지 않음 |
| hold 의미 | 자동 발사만 보류. 경계·탐지·인계·확보·조준은 유지하고 발사 버튼/G의 수동 단발 허용 |
| 표적 선택 | 기존 commander 인계·gunner 자체 확보·플레이어 지정을 사용하고, 관측·발사선 상실 시 전차장 후보로 전환 (§4-4) |
| 현재 표적 유지 | 포수가 보던 표적을 1순위로 유지. 관측·발사선이 유효하지 않으면 전차장이 확인한 유효 후보를 2순위로 인계 |
| 플레이어 지정 | 지정한 표적을 즉시 1순위 임무로 삼아 확보·조준 후 자동 사격. 별도 발사 버튼/G를 요구하거나 자동 모드를 끄지 않음 |
| 격파 확인 | 확인된 잔해에 대한 기존 임무·대기 후보 정리 후 기존 관측 경로가 다음 유효 표적을 확보 |
| 사격 간격·조준 | 기존 게임 시험용 간격·조준 시간 유지. 실차 장전 시간이 구현됐다고 기록하지 않음 |

자유사격/응사만/사격금지의 3단계 ROE와 위협 점수화는 후속이다. 이번 `hold`는 수동 단발을 허용하므로 ‘사격 금지’라고 표시하지 않는다.

### 4-2. 발사 조건과 단일 실행 경로

자동 발사는 다음 기존 관문을 모두 통과했을 때만 허용한다.

- 차량과 장비가 작동 가능하고 탄약이 남아 있음.
- 해당 차량의 실제 접촉이 적으로 식별·확인됐으며 기존 인계/자체 확보 임무가 `acquired`임.
- 해당 차량 포수의 현재 관측, 정렬·조준 완료, 기존 사거리·간격 조건이 충족됨.
- 발사 직전 기존 `freshSight` 경로로 자체 현재 시야·차폐·사격선을 재검사함.

팀 접촉만 안다고 바로 쏘거나, 전차장만 본 표적을 포수 확보 없이 쏘면 안 된다. 자동교전 판단에 실제 적 HP, 숨겨진 격파 여부, 미관측 실제 위치를 직접 읽어 표적을 고르는 새 경로를 추가하지 않는다. 감지·물리 판정 내부의 실제 세계 조회와 AI의 공개 지식 사용을 구분한다.

- 자동/수동은 같은 최종 발사 함수와 비행·착탄·피해 경로를 사용한다. 자동 전용 명중·피해 함수를 만들지 않는다.
- 자동 요청은 고정 시뮬레이션 스텝에서만 만든다. RAF, UI 갱신, DOM 이벤트 조회, 시야 Worker 결과 콜백에서 발사하지 않는다.
- 한 차량의 같은 스텝에 수동 요청과 자동 조건이 겹쳐도 발사·탄수 감소는 한 번이다. 이미 있는 수동 대기 요청을 자동 요청으로 덮어쓰지 않는다.
- 대기 요청에 출처를 구분하는 등, `hold` 전환 시 아직 실행하지 않은 자동 요청만 정리할 수 있게 한다. 이미 발사한 탄은 모드 전환·명령 취소·사수 격파 후에도 해결한다.
- 모드 전환·판단·상태 조회로 hit/zone 난수를 소비하지 않는다. 발사 시 명중을 새로 추첨하지 않으며 착탄 ID당 피해 한 번을 유지한다.
- 사격 모드, 대기 요청, 자동 상태는 유닛별 런타임이다. 불변 공용 프로파일에 현재 명령 상태를 넣지 않는다.
- 발사 불가 사유를 매 틱 무제한 로그에 쌓지 않는다. 상태 변화 중심으로 기록한다.

### 4-3. 고정 스텝 순서와 재표적

기존 코드에서는 관측/인계와 조준 갱신 후, 대기 수동 발사를 실행하고 해당 스텝에 도달한 착탄을 해결한다. 자동화를 넣은 뒤의 단계 순서를 문서화한다. 수동 보류 모드의 기존 판정 순서와 동결 기준표를 유지한다.

- 조준 완료를 갱신한 뒤 자동 요청을 판단하고, 공통 발사 직전 검사를 거쳐 한 번 실행한다. 별도 컨트롤러를 쓰더라도 조준 상태를 중복 진행시키지 않는다.
- 표적 교체·현재 관측 상실·명령 취소 시 기존 조준/속도 추정 리셋 계약을 따른다.
- 표적의 격파를 팀이 확인한 경우 관련 인계·추적·대기 후보와 선택 표적을 정리한다. 기존 경계 모드로 다음 후보를 찾을 수 있어야 한다.
- 미확인 격파의 경우 비공개 사실로 공개 임무가 즉시 ‘격파 완료’가 되거나 성공 알림이 나면 안 된다. 현재 관측·재식별·기존 임무 만료 경로로 처리한다.
- 두 차량이 같은 스텝에 발사·격파되거나 여러 탄이 같은 시각 도달하는 경우를 고정 순서로 재현 가능하게 한다. 이미 발사된 탄을 삭제하지 않는다.
- 자동 발사를 위해 적 전체를 추가 전수 탐색하거나 LOS를 다시 중복 계산하지 않는다. 기존 관측 임무와 사격 준비 상태를 사용한다.

### 4-4. 포수 현재 표적 → 전차장 다음 후보 인계 [사용자 추가 결정]

플레이어의 새 표적 지정은 현재 임무보다 우선한다. 별도 지정이 없을 때 현재 포수 임무를 유지하고 전차장 후보는 다음 순서로 사용한다. 실제 장비별 위협·방호력 점수를 만드는 기능은 포함하지 않는다.

1. **1순위 유지:** 플레이어가 새로 지정하면 해당 표적을 우선 임무로 삼는다. 별도 지정이 없으면 포수가 현재 관측·확보하고 사격을 준비하는 표적을 유지한다. 전차장은 독립 경계를 계속하면서 다른 적의 자체 관측·식별 결과를 후보 목록에 갱신한다.
2. **전환 조건:** 이미 확보했던 1순위 표적이 관측에서 벗어나거나, 현재 발사선의 실제 차폐 때문에 사격각을 확보할 수 없다면 전차장의 유효한 다음 후보로 헌터킬러 인계한다. 관측을 잃은 표적의 숨은 실제 위치를 계속 추적하며 기다리지 않는다.
3. **후보 근거:** 2순위는 해당 차량 전차장이 자체 관측으로 적임을 식별·확인한 후보여야 한다. 관측 시점·기존 유효기간을 검사하고 미식별·만료·확인된 잔해를 제외한다. 팀 공유 목록이나 전체 적 실제 좌표를 전차장 관측으로 대체하지 않는다. 유효 후보가 여럿이면 §4-5의 전차장 최초 발견 시각 순으로 사용한다.
4. **인계 후:** 전차장이 확인한 관측 위치로 포수가 선회하고, 포수 자신의 실제 시야로 재확보·정렬·조준한 뒤 발사한다. 인계만으로 `acquired`나 `ready`를 강제하지 않는다. 전차장은 다음 후보 경계를 계속한다.
5. **후보 없음:** 유효한 2순위가 없으면 기존 관측 위치·재확보·기억 만료 규칙을 따른다. 숨은 적을 새로 만들어 지정하거나 관측 조건을 완화하지 않는다.

전환 상태는 다음과 같이 구분한다.

| 상태 | 표적 처리 |
|---|---|
| 현재 표적의 관측·발사선 유효 | 현재 표적 유지 |
| 짧은 관측 끊김, 기존 `lossGrace` 안에서 재확보 | 기존 상실 유예 규칙으로 유지. 새 고정 지연 수치는 추가하지 않음 |
| 관측 상실 유예 이후에도 재확보 실패 + 유효 전차장 후보 있음 | 다음 후보로 인계 |
| 현재 확보 표적에 `freshSight`의 실제 발사선 차폐가 확인됨 + 유효 전차장 후보 있음 | 다음 후보로 인계. `gunnerCurrent`가 유지된다는 이유만으로 차폐 표적에 고정하지 않음 |
| 발사 간격·탄약 대기, 아직 조준 중 | 이것만으로 표적을 바꾸지 않음 |
| 다음 후보로 인계받아 포탑 선회·자체 확보 중 | 기존 확보/만료 규칙으로 해당 인계를 진행. 선회 중 관측 없음이나 정렬 오차를 또 다른 전환 사유로 오판하지 않음 |

- 표적 A에서 B로 전환한 뒤 A가 다시 보이더라도 B가 유효하면 B를 유지한다. 고정 스텝마다 A/B 사이를 왕복하지 않는다.
- B 자체 확보가 실패·만료되면 기존 재방문 유예/후보 유효기간을 적용해 다음 선택을 한다. 새 임의 전환 확률은 넣지 않는다.
- 표적 변경 때 A에 묶인 미실행 발사 요청과 조준 상태를 정리하고 B의 기존 준비 과정을 시작한다. 이미 A를 향해 발사한 탄은 그대로 해결한다.
- `auto`/`hold`는 자동 발사 허용 모드다. hold에서도 기존 관측·인계는 계속되므로 이번 후보 인계도 가능하되 자동 발사는 하지 않는다. 명시적인 포수 지점 경계·지정 취소의 기존 명령 우선권과 재획득 지연은 유지한다.
- 전환 이유는 해당 차량의 관측 상실·확인된 차폐·유효 후보 인계로 기록한다. 실제 적 HP나 미확인 격파 여부로 이유를 만들지 않는다.

### 4-5. 자동사격 기본·플레이어 우선 지정·발견 순 후보 [최신 사용자 확정]

**일반 운용 흐름:** 자동사격이 기본으로 작동한다. 플레이어는 필요할 때 우선 표적을 지정하며, 지정된 차량은 그 표적을 확보·조준한 뒤 스스로 사격한다. 전차장이 확인한 다른 적은 발견 순서대로 다음 후보가 된다.

- 정상 차량 생성 API와 시나리오 초기화 모두 기본 `auto`다. 기존 수동 검사에는 `hold`를 명시해서 판정 계약을 보존한다. 정상 시나리오만 auto로 덮어쓰고 공통 생성 기본은 hold로 남겨두는 구현은 이 최신 결정과 다르다.
- 플레이어가 D를 새로 지정하면 현재 A를 상대하던 포수의 우선 임무를 D로 바꾼다. 지정은 자동사격을 해제하거나 수동 발사 대기 모드로 바꾸는 명령이 아니다. D에도 기존 자체 관측·식별·확보·정렬·발사선 조건을 적용한다.
- 정상 auto 상태의 표적 지정 후에는 발사 버튼/G 입력 없이 실제 발사까지 진행해야 한다. 별도로 명시한 자동사격 보류는 별개 명령이며, 표적 지정 자체로 모드를 변경하지 않는다.
- 현재 임무가 유효한 동안은 유지한다. 격파 확인·관측 상실 유예 종료·실제 발사선 차폐 등 기존 전환 조건이 충족되면 전차장 다음 후보를 인계한다. 플레이어의 새 지정은 그보다 우선한다.

**발견 순 후보 규칙:**

1. 해당 차량 전차장이 적을 처음 실제로 발견한 시뮬레이션 시각을 기록한다. 전차장 자체 관측 기준이며 전체 유닛 배열·적 실제 ID·공유 접촉 생성 순서를 발견 순서로 대체하지 않는다.
2. 전차장이 적으로 식별·확인한 뒤에만 교전 가능한 후보에 자동 등록한다. 발견했지만 미식별인 접촉은 앞에서 대기열을 막지 않는다.
3. 후보 선택은 **전차장 최초 발견 시각 오름차순**이다. 같은 시각이면 결정적인 보조 순서로 고정한다. 최초 발견과 식별 완료 시각을 별도로 보존해 둘을 혼동하지 않는다.
4. 같은 적의 재관측은 관측 위치·유효시각을 갱신한다. 최초 발견 순서를 바꾸거나 같은 적을 중복 등록하지 않는다. 발견 순서 메타데이터만 보존하며 만료된 위치·관측을 계속 유효하게 만드는 데 쓰지 않는다.
5. 가장 앞 후보가 만료·미확보 실패 유예·확인된 잔해 등으로 현재 사용할 수 없으면 다음 유효 후보를 확인한다. 뒤 후보를 선택하려고 앞 후보의 관측 조건을 완화하지 않는다.
6. 식별 완료 시각 차이로 뒤늦게 유효 후보가 추가돼도 이미 유효하게 수행 중인 임무를 끊지 않는다. 다음 표적을 고르는 시점에 발견 순서를 적용한다.
7. 포수 임무가 해제된 뒤 전차장 유효 후보가 있다면 이 순서를 먼저 적용한다. 기존 `Object.entries(...).find(...)`의 포수 자체 접촉 순서가 전차장 후보보다 무조건 앞서서 발견 순서를 무효화하지 않게 한다. 후보가 없으면 기존 포수 자체 발견 경로를 사용할 수 있다.
8. 시나리오 초기화 시 이전 발견 순서·후보·우선 지정·격파 상태가 남지 않는다.

**최신 검토에서 남은 예외:** `1f5201a`의 hold 차폐 검사는 관측자/현재 표적의 위치·자세가 변할 때만 다시 실행된다. 처음 A가 차폐됐을 때 B가 없다가, 나중에 전차장이 B를 식별해도 A/B 자세가 그대로면 hold에서 인계가 멈춘다. 자동사격이 기본이라는 정책과 별도로, 보류가 관측·인계를 중단시키지 않는 기존 계약을 유지하려면 이를 고친다. 차폐 결과 캐시와 후보 목록의 재평가를 분리하거나 후보 변화도 갱신 조건에 포함한다. 새 후보 발견 때마다 모든 LOS를 중복 계산하는 방식은 피한다.

## 5. UI·공개 정보·Worker

- 선택한 생존 아군에 자동 사격/보류 전환을 작게 제공하고 모드·현재 동작·발사 대기 사유를 표시한다. 차량 선택을 바꿔도 각 차량의 모드는 독립적으로 유지한다.
- 플레이어가 명령할 수 있는 UI는 아군에 한정한다. 적도 내부적으로 같은 자동교전 코드를 사용한다.
- 수동 발사 버튼/G, 지정·취소·경계, 일시정지·배속·초기화의 의미를 유지한다. 지정 취소 뒤 기존 자동 재획득 지연을 존중한다.
- 자동 여부와 관계없이 미관측 착탄/피해/격파는 기존 공개 규칙과 잔해 확인 규칙을 따른다. 자동 상태·사유·개발 snapshot에 숨은 적 ID/HP/좌표가 새지 않아야 한다.
- 적 자동 사격의 실제 발사는 코어에서 진행한다. 적 발사 이벤트·포구 섬광·비행을 청색 화면에 전역 공개하는 기능은 이번에 추가하지 않는다. 아군 자체 피해는 아군 정보로 갱신한다.
- WIP10부터 남아 있는 ‘미관측 빗나감 먼지’ 공개 문제는 별도 정책 미결정이다. 이번 두 버그 수정으로 정보 공개 문제 전부를 해결했다고 기록하지 않는다.
- 새 모듈/설정을 추가했다면 페이지, 빌드, Node 로더, 내보내기와 실제 내장 Worker의 의존성을 확인한다. 시야 Worker에 자동 사격·피해를 중복 실행시키지 않는다.

## 6. 작업 순서

1. 기존 브랜치에 최신 main을 동기화하고 WIP11A 기준선과 사용자 잔해 문서를 보존한다.
2. 두 잔해 문제의 재현 검사 작성 → 관측/잔해/선택 수정 → 해당 검사 통과.
3. `auto`/`hold` 런타임과 공통 발사 경로 연결 → 양측 자동교전 통합 검사.
4. UI와 선택 없음 처리, 공개 정보·기억 접촉·초기화 확인.
5. 전체 회귀, 브라우저, 성능·빌드·패키지 검증 후 문서/PR 갱신.

한 번에 제출하되 위 순서로 검증 결과를 나눈다. 잔해 문제를 자동교전 코드로 덮어서 원인과 재현 여부를 잃지 않는다.

## 7. 필수 검증

WIP11A에서 독립 재확인한 기준선은 **177개 Node 규칙/코어 + 입력 35 + 지도 16 + 시야 12 + 차량/Worker 9 = 249개 통과**다. 새 버전은 이 기준선과 새 검사를 구분해 보고한다. 검사 개수를 맞추려고 합치거나 삭제하지 않는다.
최신 WIP11B `1f5201a`에서는 **192 + 37 + 16 + 12 + 9 = 266개 통과**를 재확인했다. 아래 추가 정책 검사와 늦게 발견한 후보의 인계 재현은 이 기준선에 추가한다. 기존 검사 통과가 새 정책의 완료를 뜻하지 않는다.

순수 상태 검사와 **실제 TacticalCore 통합 검사**를 모두 둔다. 자동교전 통합 검사는 임의로 contact/`acquired`/`ready`를 주입한 것만으로 대체하지 않는다. 실제 관측 누적과 인계·조준을 거치는 합성 전장 사례를 포함한다. 잔해 재발견과 양측 자동교전을 각각 검증한다. 전차장이 B를 실제로 관측·식별해둔 상태에서 포수의 A 관측 또는 A 발사선만 차폐하는 다중 표적 사례로 E13~E17을 검사한다.

기존 수동 검사의 시나리오에는 hold를 명시한다. 이는 수동 입력 계약을 보존하기 위한 fixture 설정이며, 실행 기본 auto를 검사하지 않는 핑계가 되어서는 안 된다. 별도의 실제 시나리오 기본값 검사와 양측 자동 사격 검사를 둔다. 동결 기준표를 현재 결과로 다시 생성해 통과시키지 않는다.

## 8. 브라우저·성능 확인

실제 브라우저에서 단일 HTML을 열고 다음을 확인한다.

1. 양측 기본 auto, 발사 버튼을 누르지 않은 교전, 아군 HP 감소와 격파.
2. 차량별 auto/hold 전환, 수동 단발, 다른 차량 선택 뒤 모드 유지.
3. 관측한 잔해·미관측 격파 후 재식별·영구 표시·클릭 불가.
4. 선택 중인 아군 격파와 전 아군 격파 후 화면·카메라·초기화.
5. 일시정지·배속·초기화와 데스크톱, 모바일 가로/세로 viewport.
6. 실제 내장 시야 Worker와 페이지 오류 없음.
7. 포수가 A를 확보하는 동안 전차장이 B를 식별 → A 관측/발사선 상실 → B 인계·포수 재확보·사격. B 선회 도중이나 A 재등장 때 표적 왕복 없음.

브라우저 실행은 직접 시도한다. 이번 검토 환경에서는 Chromium이 `socket() failed: Operation not permitted`로 시작하지 못했으며, 이전 작업자의 17/17 기록을 이번 실행 결과로 재사용하면 안 된다. HTTP/`file://`, viewport/실기기, 성공/차단을 구분한다.

기존 관측 벤치마크를 같은 조건으로 실행하고, 자동 사격 모드가 켜진 합성 다수 차량의 고정 스텝 CPU 비용과 다중 착탄을 추가 확인한다. 실제 활성 auto 상태로 측정하며 HP·격파·재표적도 점검한다. 측정 조건과 중앙값/P95, 로그 저장량을 남긴다. CPU 시간을 전체 게임 FPS로 환산하지 않는다. 지도 재수집·재베이크는 하지 않는다.
