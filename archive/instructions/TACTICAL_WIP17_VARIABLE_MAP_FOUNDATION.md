## 2. 현재 코드에서 확인한 전제

- `sim-core.js`는 `meta.width/height`를 읽지만 초기 검사에서 두 값이 4000인 경우만 허용한다. 이 검사를 단순 삭제하는 것으로 작업을 끝내지 않는다.
- 지붕 미리보기 격자는 배열 크기를 지표 규격으로 만들면서도 경계 999, 행 간격 1000, 좌표 간격 4를 고정 사용한다. 4km 바깥·직사각형에서 건물 차폐가 잘못될 수 있으므로 생성/조회 양쪽을 함께 정리한다.
- 고도·지표 조회, 길찾기 격자와 일부 LOS 요약, 카메라에는 이미 규격 기반 계산이 있다. 재사용하고 폭/높이·행/열이 뒤섞이는 부분만 정확히 고친다.
- 지도 생성기는 4000m 범위와 2000×2000 배열을, 여러 도구는 `rasdorf_4km.json`과 고정 출력 경로를 전제한다. 미래 지도도 실행 코드를 직접 편집하지 않고 같은 도구 흐름에 넣을 수 있어야 한다.
- 숫자 검색 결과를 일괄 치환하지 않는다. 예를 들어 1000은 mm/밀·ms 환산에도 쓰이고 500m 버킷·32m LOS 타일·0.05초 틱은 지도 크기와 다른 의미다.

## 3. 맵 규격과 데이터 계약

- 가로/세로 미터 크기, 고도/지표의 간격·행/열·표본 원점, 길찾기 간격·행/열, 지도 ID/소스 해시를 한 곳에서 일관되게 해석하는 작은 규격 계층을 둔다. 같은 계산을 여러 모듈에 복제하지 않는다.
- 기존 지도 메타데이터를 원천으로 사용한다. 폭/높이와 격자 수를 각각 임의 지정해 모순을 만드는 구조는 피한다. 기존 4×4 데이터는 호환 경로로 그대로 읽을 수 있어야 한다.
- 이번 지원은 4×4·8×8km와 직사각형 검증 범위다. 허용하는 정수 크기·고도/지표 셀 정렬 조건과 해상도 계약을 명시한다. 미지원 정렬/간격은 조용히 자르거나 보정하지 말고 명확히 거부한다.
- 가로와 세로를 독립 계산한다. 인덱스는 실제 열 수를 행 간격으로 사용하고 경계는 해당 격자의 행/열과 미터 범위로 계산한다. ceil/floor·표본 중심·마지막 유효 셀의 의미를 통일한다.
- 길찾기처럼 크기가 간격으로 나누어떨어지지 않는 경우의 마지막 부분 셀을 명시한다. 월드 바깥 셀을 통행 가능하게 만들거나 목표 좌표를 늘리지 않는다. 지원 계약상 거부할 경우에도 일관되게 검사한다.
- 폭/높이·간격·행/열의 유한 양수와 정수 조건, 곱의 안전성, 예상 배열/디코딩 길이, 고도 표본 범위, 파생자료 규격을 큰 배열 할당이나 사용 전에 검증한다. 잘못된 값이 NaN·인덱스 초과·불필요한 대형 할당으로 이어지지 않게 한다.
- 지도 크기가 달라도 로컬 월드 좌표의 축·미터 단위와 고도 표본 중심 규칙은 유지한다. 원본 좌표계/크롭 범위에서 로컬 좌표로 변환하는 과정은 생성 설정과 함께 기록한다.
- 해상도를 자유롭게 바꾸는 별도 기능은 요구하지 않는다. 현재 2m/4m/16m 계약을 검증하고 지도 면적과 해상도를 혼동하지 않으면 된다.

## 4. 실행 코드·캐시·표시 연결

| 영역 | 요구사항 |
|---|---|
| 지면/지표/지붕 | 생성과 조회의 행 간격·경계를 실제 규격에서 도출. 오른쪽/아래 끝과 4km 바깥에서 다른 셀을 읽지 않음 |
| 건물·숲 공간 인덱스 | 버킷 열/행과 key를 전체 폭/높이에 맞춤. 지도 일부만 인덱싱하거나 다른 행과 충돌하지 않음 |
| 이동·충돌·길찾기 | 시작/목표·실제 선분 통과·경계 판정 일치. 맵별 nav 행/열·배열 길이·계약·소스 해시 검증 |
| LOS·노출·발사선 | 기존 9표본·2m 정밀 판정·정적 요약·캐시 동등성 유지. 4km 경계에서 잘못 종료하거나 미리보기 지붕을 잘못 읽지 않음 |
| Worker | 메인과 같은 맵 규격·데이터·모듈로 구성. 자료 불일치를 성공으로 숨기거나 잘못된 4km 자료로 계산하지 않음 |
| 카메라·입력·표시 | 전체 맞춤·이동/확대 경계·클릭 좌표·지도 테두리·시야 오버레이를 가로/세로별로 처리. 크기 표시는 활성 메타데이터 기준 |
| 전투·AI | 월드 좌표가 4km 밖이어도 정상 작동. 사거리·속도·장전·판단 주기·기존 게임 계수와 숨은 정보 규칙 유지 |

- 필수 파생자료의 소스 해시·행/열·간격·계약이 현재 지도와 맞지 않으면 명확히 거부한다. 선택적 표시 자료의 부재에 대한 기존 정상 폴백과 다른 지도 자료의 잘못된 연결은 구분한다.
- 기존 4×4의 지면 높이·지표·건물·LOS·경로·전투 결과를 보존한다. 원본 지도, 현재 지도 해시와 파생 벡터/길찾기 캐시는 크기 일반화를 이유로 재설계하거나 새 지형으로 바꾸지 않는다.
- 새 공통 모듈이 생기면 실제 페이지·단일 HTML·내장 Worker·Node 로더·테스트 팩토리·지도 생성/벤치마크 스크립트의 모든 로드 경로를 연결한다. 테스트용 대체 코어에서만 성공하면 완료가 아니다.
- 현재 앱은 한 맵을 내장한 빌드다. 실행 중 맵 교체·복수 지도 동시 상주·지도 목록 UI는 도입하지 않는다. 기존 reset·Worker 취소/폴백·가로 화면 게이트는 유지한다.

## 5. 생성·빌드 도구의 기틀

- 맵 입력/출력 경로와 원본 크롭·해상도 규격을 명시적으로 전달할 수 있게 정리한다. 설정 파일 또는 CLI 중 기존 구조에 맞는 방식을 쓰고, 기존 명령을 인자 없이 실행하면 현재 4×4 기본 경로로 동작하게 한다.
- `build_battlefield.py`의 고정 배열 크기·필터 슬라이스·행 인코딩 수를 설정에서 도출한다. 실제 원본이 지정 범위를 덮지 못하거나 NoData가 있으면 실패시킨다. 현재 4km 원본을 늘여서 다른 면적의 실측 지도로 만들지 않는다.
- navigation·등고선·지형 판독성 도구는 지정한 입력의 규격과 소스 해시를 사용하고 지정 출력에 저장한다. 기본 입력 파일명을 스크립트마다 편집해야 새 지도를 넣을 수 있는 구조를 남기지 않는다.
- HTML 빌드도 서로 일치하는 지도·등고선·지형 판독성 자료 묶음을 선택할 수 있어야 한다. 기본은 현재 4×4이며 합성 테스트 빌드는 별도 출력에 둔다. 다른 맵 자료를 섞으면 검출한다.
- 기본 입력으로 생성되는 기존 지면·지표·벡터·길찾기 데이터는 그대로 재현해야 한다. 메타데이터 변경이 꼭 필요하면 호환 방식·차이를 설명하고 지형 내용·캐시 결과가 바뀌지 않은 증거를 남긴다.
- 원본 4×4 데이터/출처를 검증하는 전용 검사도 유지한다. 이 검사의 4km 기준까지 모두 메타데이터로 바꿔 잘못된 원본을 통과시키지 않는다. 일반 규격 검사는 별도로 추가한다.
- 완료 문서에 기본 4×4 빌드와 합성 다른 규격 빌드의 재현 명령, 향후 실제 8×8 원본을 준비했을 때 교체할 설정/입력/출력 경로를 적는다. 실제 원본 다운로드나 제품용 8×8 제작은 수행하지 않는다.

## 6. 검증·성능 기준

기본 4×4는 기존 실측 지도 회귀로, 다른 크기는 명시적 합성 fixture로 검증한다. 큰 fixture는 생성기로 만들고 필요한 검사에서만 순차적으로 사용해 배열·브라우저/Worker의 불필요한 중복 상주를 피한다.

| 검증 묶음 | 필수 사례 |
|---|---|
| 규격 계약 | 유효 4×4/8×8, 비정사각형, 미지원 셀 정렬·간격, 0/음수/NaN·과도한 크기, 행/열·배열 길이·소스 해시 불일치 |
| 좌표·행 간격 | 네 모서리·마지막 셀·경계 안팎, x와 y가 다른 직사각형, 4km 바깥의 비대칭 고도/지표/건물 표본. 평탄한 0 값만으로 잘못된 인덱스를 숨기지 않음 |
| 이동·경로 | 시작/목표가 모두 4km 밖인 이동, 기존 4km 경계를 넘는 이동, 긴 경로·우회/실패, 월드 바깥 목표 거절과 실제 선분 충돌 |
| 관측·전투 | 4km 바깥에 배치된 가까운 두 차량의 정상 탐지·인계·사격·이펙트. 기존 관측/사격 거리와 부분 차폐·발사선 판정 유지 |
| 메인/Worker | 합성 8×8의 4km 밖 관측자에서 실제 내장 Worker를 실행하고 직접 계산과 경계·차폐 결과 비교. 정상 폴백/취소·자료 불일치 검출 |
| 실제 앱 | 기본 4×4 시작/초기화/입력 회귀. 별도 합성 8×8 및 직사각형 앱의 맞춤/줌/팬·클릭 이동·테두리/시야 오버레이·잘림/가로 넘침 검사 |
| 도구·캐시 | 기본 명령 호환, 다른 입력/출력 선택, 다른 맵 캐시 혼입 거부, 생성/빌드 재현성, 기본 지도·파생자료 내용 보존 |
| WIP16 회귀 | 지속 차폐 단일 복귀, 수동 지정의 소유권/범위 처리, 능선 전후진 후 자동 재교전, halt의 무발사 검사와 첫 발 정차 조건 유지 |

- 합성 8×8은 실제 8000×8000m 범위와 현재 해상도 계약으로 Node와 실제 Chromium에서 한 번 이상 끝까지 실행한다. 작은 격자의 메타데이터만 8km로 바꾸거나 해상도를 낮춰 대신하지 않는다.
- 폭/높이 혼동은 별도 직사각형 fixture로 잡는다. 작은 비정사각형 단위 검사와 큰 실제 범위 검사를 조합해도 된다. nav 부분 셀 처리는 지원 계약에 맞춰 검사한다.
- 대형 fixture의 길찾기는 일치하는 사전 캐시를 준비할 수 있다. 정상 앱 로딩을 매번 전체 지도 현장 bake로 대체하지 않는다. 지형과 다른 캐시를 임의로 재사용하지 않는다.
- 같은 유닛 수·배치 관계·관측 거리로 4×4와 합성 8×8의 초기화 시간, 메인/Worker 준비, 메모리 추정/가능한 실측, 전체 틱·렌더·짧은/긴 경로의 중앙값/P95·방문 셀·할당 범위를 기록한다. 메인/Worker의 별도 코어·원본/디코딩 중간 배열도 고려한다.
- 고도 Float32 배열만 16MB→64MB로 늘어난다는 산술 추정을 전체 앱 메모리나 실측으로 보고하지 않는다. 맵 면적 4배와 실시간 교전 CPU 4배를 동일시하지 않는다.
- 기존 4×4를 같은 조건의 main과 비교해 의미 있는 회귀를 확인한다. 크기 일반화를 위해 불필요한 전체 지도 순회나 매 프레임 규격 계산을 추가하지 않는다. 측정된 병목만 필요한 범위에서 다루고 알고리즘 전면 교체는 후속으로 남긴다.
- 저장소의 Node·실제 Chromium·Python 지형/소스 검사와 빌드를 수행한다. 기존 4×4 정확성·WIP11~16 검사를 삭제하거나 약화하지 않는다. 실행하지 못한 범위와 이전 버전 결과를 구분한다.

## 7. 제출물·완료 상태

- 구현 브랜치/커밋, 공통 규격·좌표/격자 계약, 수정한 고정 전제와 유지한 해상도, 캐시 호환/실패 처리, 도구 입력 설정, 재현 명령·검증·비용·남은 한계를 제출한다.
- `docs/VARIABLE_MAP_FOUNDATION_WIP17.md`, `TACTICAL_RELEASE_WIP17.md`, `tests/releases/WIP17-validation.json`에 구현·릴리스·기계 판독 결과를 기록한다. 합성 크기 검증과 실제 8×8 지도 제공을 구분한다.
- 기본 4×4를 담은 WIP17 단일 HTML·ZIP·체크섬을 만든다. HTML=dist·ZIP 단일 항목/CRC/해제 바이트·반복 빌드/패키징을 검증한다. 실제 8×8 지도나 큰 합성 fixture를 기본 다운로드에 넣지 않는다.
- 완료 시 최종 지시서를 `archive/instructions/`에 보관하고 `docs/tasks/`에는 완료 안내를 남긴다. 작업 목차·아카이브 목차·진행 메모·README를 실제 상태로 갱신한다. 대형 지도 아카이브에는 지원 기반과 아직 미제작인 지도/후속 최적화를 구분해 연결한다.
- **완료 의미는 가변 크기 기반과 합성 검증이다. 실제 8×8 실지도 제작·제품 제공·모바일 성능 보장을 완료했다고 쓰지 않는다.**
