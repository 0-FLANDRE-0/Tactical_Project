## 1. 전장 규모·운용 범위

### 사용자 방향

- 이전에 검토한 **거대 전역지도에서 부대 단위 이동 → 개별 전술지도 전투** 구성은 **폐기 확정이 아니라 임시 보관**한다. 현재 개발·설계의 우선 범위로 끌어오지 않는다.
- 지금은 **각각 독립적으로 운용되는 단일 전술지도**를 우선한다. **4×4km는 현행**, **8×8km는 확장 후보**, **9×12km는 가능하면 지원할 추가 후보**로 남긴다. 어떤 크기를 기본/최대 맵으로 지정할지, 제공할 지도 목록은 미정이다.
- TACTICAL은 전차만 운용하는 게임이 아니라 보병·포병·방공·헬기·항공기·드론 등으로 확장하는 **제병협동 RTS**를 지향한다.
- **포병도 현재 전술지도에 배치되고 이동·사격하는 실제 유닛**이어야 한다. 단순한 화면 밖 지원 버튼만으로 대체하지 않는 방향이다. 이로써 포병의 재배치, 손실, 관측·대포병 사격 등 게임 플레이가 가능해야 한다.
- 수백 개 유닛을 상시 직접 조작하는 규모를 지금 목표로 삼지는 않는다. **구체 유닛 상한/분대 수는 아직 확정하지 않았다.** 맵 면적이 커진다고 유닛 수가 면적 비례로 늘어야 하는 것도 아니다.
- **포병 최대 사거리가 지도 전체보다 길 수 있다는 점은 인지**한다. 지도 크기를 늘리는 것만으로 포병의 전역 커버 문제가 사라진다고 가정하지 않는다. 탐지·탄약·운용 조건·게임 밸런스는 후속 논의한다.

### 지도 크기별 데이터 비교 (기존 해상도 유지 시 산술 추정)

현재 라스도르프 기준: 고도 2m 간격, 지표 분류 4m 간격, 길찾기 16m 격자. 아래는 **격자 데이터의 최소 원시 배열만** 계산한 값으로 전체 메모리와 전체 HTML/ZIP 크기가 아니다.

| 맵 크기 | 면적 | 고도 표본 (2m) | Float32 고도 배열 | 4m 지표 바이트 | 16m 경로 격자 |
|---|---:|---:|---:|---:|---:|
| 4×4km | 16km² | 2,000×2,000 = 400만 | 16.0 MB | 1.00 MB | 250×250 = 62,500 |
| 8×8km | 64km² | 4,000×4,000 = 1,600만 | 64.0 MB | 4.00 MB | 500×500 = 250,000 |
| 9×12km | 108km² | 4,500×6,000 = 2,700만 | 108.0 MB | 6.75 MB | **563×750 = 422,250** |

- **정정:** 앞선 대화의 '9×12km / 16m 경로 격자 562,500개'는 계산 오류다. `ceil(9000/16) × ceil(12000/16) = 563 × 750 = 422,250`이 맞다.
- 계산은 단위를 **십진 MB**로 표시했다. 고도 배열, 지표 분류 외에도 인코딩된 원본, 디코딩 중간 배열, 건물·도로·수목·등고선, 길찾기·LOS 가속자료, 화면 캔버스, **메인 스레드/Worker의 별도 코어** 등이 메모리를 차지한다.
- 4×4에서 8×8은 면적 4배, 9×12는 6.75배다. **메모리·초기 로딩 비용의 증가와 실시간 CPU의 증가를 동일시하지 않는다.** LOS는 유닛 밀도·관측 관계, 렌더링은 화면 범위·카메라 움직임, 길찾기는 실제 검색 범위에 좌우된다.
- 브라우저 단일 HTML·오프라인 실행 형식은 현행 유지. 8×8/9×12에서 파일이 얼마로 늘어날지, 모바일에서 가능한지 **실제로 제작·프로파일링하기 전에는 확정할 수 없다**.

## 2. 현행 구현: 경로탐색은 이미 경사 통과 제한을 사용

검토한 WIP11C 브랜치의 `src/sim-core.js`:

- `passable()`: 맵 경계, **지형 경사**(`slopeAt > VEHICLE.maxSlope`), 건물·수역·근접 차량 등을 검사한다. 진행 방향이 주어지면 `gradeAt/gradePassable`로 **종방향·횡방향 경사 제한**도 확인한다. 임계값은 차량 게임 프로파일의 경사율/기동 설정이며 '모든 차량 공통의 고정 각도'로 바꾸자는 결정은 없다.
- `WORLD.nav=16`m 격자에서 **A\*** 검색, 8방향 연결·지표 통행 비용·경사 비용, `segmentClear()` 경로 연결 검증과 부드럽게 줄이기(smoothing)를 수행한다.
- 정적 통행비와 연결 관계를 미리 제작한 `MAP.navigation` 캐시에서 복원한다. 매 명령에 전 세계의 경사·건물 지도를 처음부터 굽는 구조는 아니다.
- 단, `planPath()`는 검색마다 `dist(Float64Array)`, `prev(Int32Array)`, `closed(Uint8Array)`를 **전체 경로 격자 수만큼 생성·초기화**한다. 경로가 짧아도 기본 배열 할당 부담은 맵 면적에 따라 증가한다.

### 경로탐색 후속 최적화 [제안 — 미구현]

1. **탐색 배열 재사용 + 세대/방문 마커:** 매 경로 요청마다 전체 배열을 지우지 않고 해당 검색에서 방문한 셀만 초기화하여 할당·GC 부담을 낮춘다. 세대 넘침, 재진입, 동시 요청은 별도 설계한다.
2. **계층형 A\***: 큰 지도에서 장거리 이동 시 성긴 상위 격자로 대략적인 통로를 찾고, 좁힌 구간에 기존 16m 세부 탐색을 적용한다. **실제 지나갈 길이 존재하는데 조기 실패하는 일을 방지하도록 통로 확장/전체 탐색 폴백**을 둔다.
3. **정적·동적 장애물 분리:** 지형·경사·고정 건물은 사전 구운 연결 그래프를 사용하고, 주변 차량은 근거리 회피나 부분적 경로 조정으로 처리하는 방안을 검토한다. 기존 안전거리·최종 통과 가능성의 의미를 유지한다.
4. **같은 이동 목적의 부대 경로 일부 공유:** 분대·차량 대열은 상위 이동 경로를 재사용하고, 개별 유닛은 최종 배치·충돌 회피를 별도로 한다. 획일적인 경로 공유로 부대가 서로 막히지 않도록 한다.
5. **벤치마크 필요:** 요청당 방문 셀, 할당량, 지연시간의 중앙/P95, 긴 우회·가파른 능선·도로·좁은 통로·이동 장애물·검색 실패 사례를 현재 A\*와 대조한다. 아직 실제 성능 개선 배율은 측정하지 않았다.

## 3. 현행 구현: 관측·LOS가 비교적 비싼 반복 계산

검토한 WIP11C 브랜치의 `src/sim-core.js`, `src/observation.js`:

- 관측 후보를 **500m 공간 버킷**과 센서 거리/FOV로 먼저 걸러내고, 정밀 관측을 **10Hz 분산 스케줄**로 수행한다(고정 시뮬레이션 스텝 0.05s).
- 한 차량의 노출은 **차체 6 + 포탑 3 = 9개 표본**으로 판단해 부분 엄폐와 헐다운을 표현한다.
- LOS는 지형 고도를 기반으로 건물·숲 차폐까지 판단한다. 정밀 광선 기준 2m 간격의 검사 흐름을 유지하면서 **32m 타일별 최대 지형/지붕 높이 및 숲 요약**으로 확실히 안전한 구간을 건너뛴다. 캐시된 광선 결과는 **정확히 같은 관측 위치·피격 표본**인 경우 제한된 시간 동안 재사용하며, 움직임·자세 변화 시 무효화한다.
- 정적 32m 타일 요약은 기준 판정과 결과가 동등하도록 보수적으로 설계·검증돼 있다. 이 최적화가 **LOS 결과를 근사화하거나 정확도를 희생한 방식은 아니다**.

### LOS 후속 최적화 [제안 — 미구현]

1. **정밀 광선을 시작하기 전에 보수적으로 탈락·통과할 수 있는 관측 조건 탐색:** 시야각·거리·차폐 요약, 전체 노출 외곽 범위를 활용하되 **전차 중앙 1점만 가려졌다는 이유로 차체·포탑 9개 표본 전체를 가리는 오판은 금지**한다.
2. **공유 가능한 계산 중복 제거:** 동일 관측자/표적/광학 높이/표본과 상태 버전의 조회가 여러 경로에서 반복된다면 조회를 합치거나 제한적 캐시를 늘리는 방안을 검토한다. 조금이라도 자세·위치가 달라지는 상황을 같은 결과로 합치지 않는다.
3. **정적 지형 고도/건물의 32m 요약을 보완**하여 경로가 충분히 높은 구간은 더 빨리 건너뛰도록 검증. 건물 경계, 숲 광학 깊이, 접선 능선 등에서 기준과 달라지지 않아야 한다.
4. **동적 관측 주기**는 별도 후보: 멀거나 활동이 없는 대상의 갱신 빈도를 낮출 수 있지만 **탐지·대응 지연과 게임 밸런스가 변하므로 사용자 승인 없이 도입하지 않는다**.
5. **9표본→3표본 감소는 기본 권장안이 아님.** 게임 핵심인 부분 엄폐/헐다운 정확도가 떨어질 수 있으므로, 우선은 **9표본 유지 + 불필요한 정밀 광선 생략**을 추진한다.
6. 회귀 검사는 `visible`, `reason`, `forestDepth`, 차체/포탑 노출, **9개 표본별 결과**, 시드 재현성, 실제 이동·엄폐·건물/능선/숲 테스트를 대조하고 성능 P95도 재측정한다.

## 4. 참고 성능값과 해석

**WIP11C 브랜치 저장 벤치마크** (AMD EPYC 9V74 서버급 CPU, Node 24). **이번 아카이브 작업에서 새로 실행한 테스트가 아니라 코드·저장된 결과를 읽은 것**이다.

| 측정 범위 | 조건 | 고정 스텝 중앙 | P95 |
|---|---|---:|---:|
| 관측 포함 시뮬레이션 | 정지 50대 | 2.789ms | 5.276ms |
| 관측 포함 시뮬레이션 | 이동 50대 | 4.181ms | 5.681ms |
| 관측 포함 시뮬레이션 | 정지 100대 | 7.362ms | 15.284ms |
| 관측 포함 시뮬레이션 | 이동 100대 | **17.470ms** | **21.736ms** |
| 자동교전 포함 | 정지 100대 | 7.858ms | 14.339ms |
| **이미 해결된 착탄의 피해·상태 적용만** | 10,000건 일괄 | **19.921ms/일괄** | **27.931ms/일괄** |

- 10,000건 피해 적용은 **명중/구역 추첨, 유도·비행, 관측, 경로탐색, 렌더링을 제외한 별도의 합성 측정**이다. 표의 '스텝 시간'과 동일한 단위의 업무량으로 직접 비교하면 안 된다.
- 현재 수치로는 **관측·LOS의 반복 계산이 무거운 축**인 점은 확인할 수 있다. 하지만 **지도 렌더링과 전체 게임 중 어느 부분이 최대 병목인지는 통합 프로파일링 없이 확정할 수 없다**. 경로탐색도 이 관측 fixture에 포함되지 않았다.
- 현재 `src/map-renderer.js`는 Canvas 2D로 화면을 캐싱하지만 카메라 이동·확대에 **지형 음영을 화면 단위로 다시 생성**한다. **정적 지형의 미리 계산한 타일 음영 캐시**를 검토할 수 있으나 비용·품질 이득은 따로 측정해야 한다.
- **모바일 실기기에서의 장시간 FPS, 메모리 피크, 기기 발열/배터리, 대형 맵 초기 로딩은 미검증**이다. WIP11C 저장된 Chromium viewport 검사만으로 실기기 최적화를 입증하지 않는다.

## 5. 보병: 분대 공통 관측·판단 + 병사별 독립 피해

### 사용자 방향 — 기존 보병 아카이브의 구체화

- **보병은 분대를 기본 지휘·AI 단위**로 사용한다. **관측/탐지/상황 판단**은 병사 한 명마다 완전히 독립 실행하지 않고 **분대 단위로 계산·공유**하는 구상이다.
- **피격 여부, 피격 부위, 보호구 판정, 누적 부상·생존 상태와 파편 피격은 병사별 독립**으로 유지한다. 분대 전체에 한 번만 피해 추첨하지 않는다.
- 보병 분대가 여러 병사를 보유하더라도 **분대 수만큼 주요 관측·판단을 실행**하므로 병사별 개별 AI를 모두 실행하는 안보다 성능상 유리할 수 있다. 다만 사격하는 병사별 개별 사선이나 무기 동작, 분대원의 서로 다른 위치를 어떻게 표현할지는 미정이다.
- 분대 공통 관측의 **시점/시야 기준점**, 분대원 간 정보 공유 지연, 분대가 흩어졌을 때의 예외 처리, 분대장 사망 시 처리, 각 병사의 사격·피격 위치는 추후 정한다. 분대 공통화가 모든 병사의 물리적 위치·피격을 동일하게 만든다는 뜻은 아니다.
- 기존 [보병 설계 백업](../infantry/INFANTRY_DESIGN_NOTES_2026-11-08.md)의 **병사별 누적 피해 및 병사마다 별도 파편 피격** 설정은 변경하지 않는다.

## 6. 코드·자료 확장시 반드시 구분할 점

**현재 구현 (WIP11C 브랜치):** 4×4km 라스도르프, 2m 고도·4m 지표, 16m A\*와 경사/충돌 검사·내비게이션 캐시, 32m LOS 요약·9개 표본·10Hz 분산 관측. WIP11C는 전투/경계 UI 등의 개선을 진행한 것으로, **이 문서의 8×8/9×12 지도, 포병·보병, 새 LOS/A\* 최적화까지 구현한 것은 아니다**.

**대형 지도를 위한 선행 변경 [제안]:**
- `src/sim-core.js`의 `width !== 4000 || height !== 4000` 및 `roofGrid[y*1000+x]`·`0..999` 같은 하드코딩을 **맵 메타데이터 기반으로 일반화**한다.
- `scripts/build_battlefield.py`의 `SIZE=4000`, `width=height=2000`, `1000` 지표 격자, 고정 좌표 영역 등을 가로·세로 별도 인자로 분리한다. 직사각형 맵에서는 반드시 너비/높이를 별개로 취급한다.
- 가능한 최적화는 **메모리 피크·빌드 크기·첫 로딩 시간·화면 이동/줌 FPS·50/100 유닛 시뮬레이션 스텝·경로탐색 지연시간**을 함께 계측한다. 8×8을 검증한 뒤 9×12 확대 여부를 결정한다.
- 지도 확장은 지형 LOS·충돌 정확도와 기존 게임 데이터(차량·탄약·피해)를 보존하며 적용한다. **원본 고도 2m 간격을 단순히 4m/8m로 높여서 부하만 낮추는 것은 자동 결정하지 않는다**.
- **전역지도 아이디어 보관 상태를 계속 유지**하며 별도 확인 없이 대형 작전지도·동시 다중 맵·전역 캠페인 기능을 다음 WIP에 집어넣지 않는다.

**미정:** 지도별 유닛 최대치, 일반 전장 크기, 포병 사정권/탄약/대포병 탐지·사격 구현, 외부 장거리 포병 처리, 분대 시뮬레이션 자세한 모델, 각 최적화의 실제 성능 개선률·모바일 하한 기기.
